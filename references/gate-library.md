# 门禁判据库

> 每条门禁都写清：**判什么、判据、为什么要有它、它抓过什么**。
> 抓过真实错误的门禁才可信；没抓过任何东西的门禁只是仪式。

## 一、算量类（对表）

### G-1 公式行号对齐
- **判据**：表内 `=E{n}*G{n}` 形式的合价公式，`n` 必须等于所在行号
- **为什么**：用 `insert_rows()` 插行会平移单元格内容但**不重写公式行号**
- **抓过**：某桥梁算量表 H 列**整列错位一行**，每行金额都挂在上一行。合计只差 **−0.41%**，
  所以长期没人发现，但逐行全错（承台行显示 0、盖梁行显示承台的 92.8 万）
- **脚本**：`gate_sheet_formula.py`

### G-2 合计引用覆盖完整
- **判据**：合计行是 `=SUM(H起:H止)` 区间形式，且区间覆盖全部有效量行
- **为什么**：插行后区间没跟着扩，新行就成了"登记了但不计入合计"的幽灵行
- **抓过**：插入一行桩基钢筋后，合计区间仍是 `H3:H61`，新行 r62 没被覆盖
- **脚本**：`gate_sheet_formula.py`

### G-A 口径声明完整
- **判据**：每个数量行的名称或备注必须声明口径（单幅/全桥/单侧/两侧/单件/每座/每根）
- **为什么**：口径不明时，读者无法判断量级；自己下次也可能再次算错
- **抓过**：三条同源错误——①把纵向梁区总长当横向桥面宽（−39.4%）
  ②双幅共用桩号，只看一排（3 个承台 vs 6 个）③支座单双幅口径差点误改
- **脚本**：`gate_scope_declaration.py`

### G-B 单/全成对
- **判据**：`单幅` 出现时必须有 `全桥/两幅/双幅` 配对；`单侧` 同理
- **为什么**：只写一半等于没写
- **脚本**：`gate_scope_declaration.py`

### G-C 基准出处可查
- **判据**：每条基准的 `basis` 字段必须写"图号 + 图面位置"，不接受"按图"
- **为什么**：写不出处的基准等于假设，混进基准表会让门禁失去意义
- **脚本**：`gate_drawing_basis.py`

### G-E 量与图纸基准相符
- **判据**：表内量与基准值相对差 ≤ 容差（默认 0.5%）
- **为什么**：人工读图会错，但**错法只有有限几种**（维度错/口径错/张冠李戴），
  把已知读数做成基准表就能机器拦住
- **抓过**：承台厚度沿用另一座桥的参数（1600 vs 1500）
- **脚本**：`gate_drawing_basis.py`

### G-SUB 多小计逐组覆盖（1.2.0 ★结构性升级）
- **判据**：遍历**所有**含"小计/合计/总计"且有 SUM 公式的行，逐个验证
  ①区间内不含别的小计行（G-SUB1，否则小计套小计＝重复计数）
  ②区间恰好等于本组有效量行范围（G-SUB2，起点/终点偏一行都算错）
  ③枚举式 `=SUM(H11,H14,…)` 要么全指小计（总计型），要么恰好覆盖本组明细（G-SUB3）
  ④混合引用（既点小计又点明细）＝重复计数（G-SUB4）
- **为什么**：v1.1.0 的 `find_total_row()` 用 `max(cands)` **只取最后一个"★合计"行**、
  且只看 H 列。这个"一张表只有一个合计行"的**假设**，是漏检的根因——
  **门禁的检查对象假设错了，比判据太弱更致命**
- **抓过**：排水表 E3 有 9 个分组小计（2.2.2.1~2.2.2.8 + 总计），其中 **8 个 SUM 区间错行**，
  老门禁全绿。升级后在同一张坏表上跑出 **22 条 FAIL**（9 个小计逐个报），
  修好后 0 条——**双向回测过**
- **兼收**：总计行是 `=H3+H4+…+H64` 加法式（长表常见）也认；合计行自身是 `=E*G` 时
  不报"非 SUM 区间"（那是**门禁自己误报**，假红和漏报一样有害）
- **脚本**：`gate_sheet_formula.py`（`--list-subtotals` 可单看识别结果）

### G-OWN 单实物单入口（1.2.0 新增）
- **判据**：
  G-OWN1 [FAIL] 同码下"合计/小计/总计"行的量 ≈ 其余同码行之和（±2%）→ 汇总+明细并存
  G-OWN2 [FAIL] 同码 + 同单位 + 名称完全相同出现 >1 行
  G-OWN3 [WARN] 同 CPB + 同单位，两行部位计数相同（都写"6 墩位"）但构件词不同（墩身/墩墙）
  G-OWN4 [WARN] 同 CPB + 同单位，两行量成整数倍（2~10，±1.5%）
- **为什么**：同一个实物被开了两个计量入口，两个入口各自都"有出处、有口径、单价正常"，
  单位门禁看单价看不出来、公式门禁看行内 E×G 也看不出来
- **抓过**：桥梁表墩身 360 CM 与墩墙 420 CM **同时**按"6 个墩位"计量；实际双肢墩每墩位
  只有 2 肢、全桥 3 墩位，墩墙真值 **210 CM**。同一根因在本项目出现三次：
  墩身/墩墙、汇总行+分段明细、同码两处各写一遍
- **为什么不升 FAIL**：6 个墩位上确实可以同时有墩身和墩墙，**理论上合法**；
  但"两行都写同一个部位计数"是强信号（肢数被当墩位数就是这么错的）。
  机器摆信号，人定；升 FAIL 会逼人加白名单，白名单一多这条门禁就废了
- **假 WARN 防护**：附属项（排水/找坡/防水/涂装/标志/照明…）不参与判定——
  实测"墩顶 5% 排水找坡层（3 墩位）"会被配成墩墙的孪生兄弟
- **ack 台账（1.2.1）**：G-OWN3 接受 `--ack`——人确认"并集合法"后不再重复报警，
  但 ack 带数值指纹，量变了就报 `G-OWN3-ACKSTALE` 并要求重新确认。
  **G-OWN4 故意不接受 ack**：整倍数命中的形态就是本项目真实踩过的错法
  （肢数/幅数/根数被当成另一量），"这次是巧合"这种判断一旦能被 ack，
  这条门禁就在最关键的那一类错上失效了。整倍数只能回图纸数原始个数
- **脚本**：`gate_single_owner.py`

### G-FRESH 基准时效（1.2.0 新增）
- **判据**：
  G-FR1 [FAIL] 缺 `verified_at`（基准最近一次人工复核时间）
  G-FR2 [FAIL] 算量表 mtime 晚于 `verified_at` → 表在基准复核后被改过
  G-FR3 [FAIL] item 缺 `basis` 或写成"按图"
  G-FR4 [WARN] 有效基准项 / 数据行 < `--min-coverage`（默认 0.5）
  G-FR5 [WARN] item 缺 `asof`（该读数对应哪一版图纸）
  G-FR6 [FAIL] 缺 `drawing_set_rev`（这批基准对应哪一版图册）
- **为什么**：**门禁读的是第二份真相。基线不同步时，它越"通过"越危险。**
  实测：基准核对当日全绿 4 项，但同一天落表把承台从 14,582 改成 1,458.24——
  之所以还绿，是因为那次改的是另外几行，基准项没被触到
- **顺序铁律**：先 G-FRESH（基线可不可信）→ 再 G-E（拿可信基线比数值）。
  反过来做，就是拿过期地图导航
- **脚本**：`gate_basis_freshness.py`（`--init` 生成含时效字段的模板）

## 二、交叉类（对模型）

### G-X0 不同源检测 ★最重要
- **判据**：若两侧所有同名项数值完全一致，判**假通过**，直接 FAIL
- **为什么**：两侧同抄一个错误参数时，比对必然显示"完全一致"
- **抓过**：这不是"抓过"，是**设计目的**——这套检测专门防"校验骗过自己"
- **已抓（2026-11 海岸工程）**：某项目 13 层"模型 vs 二维"相对差**全部恰为 0.000%**，
  报告却写"交叉检核通过（独立代码路径）"。实为三维与二维共用同一断面多边形 → 同源复算。
  **本门禁本可当场判 FAIL**，因当事人自建对照表、未跑 `xcheck_model_vs_2d.py` 而漏网。
  → 配套硬规矩：**模型×二维比对必须走脚本，禁止手搓表格**（`SKILL.md` §5.2）。
- **表述纪律**：判为同源时，结论只能写"同源复算一致（仅验证算术，不验证断面读法）"，
  **不得**计入独立校验，**不得**据此写"无需回图复核"。
- **脚本**：`xcheck_model_vs_2d.py`（同源检查在比数值之前，`--stage all` 默认执行）

### G-M2 参数来源标注
- **判据**：每项必须写 `param_source`；某一侧全部同一种来源时告警
- **为什么**：`沿用上一版` 是共模错误的温床
- **脚本**：`xcheck_model_vs_2d.py`

### G-E1/E2 条目集一致
- **判据**：模型侧与二维侧的条目集合必须互为子集
- **抓过**：首轮复核的 3 个"差异"**全部是导出问题**——可选项标记漏写、
  远期口径误剔、构件漏登记，**没有一个是真算错**
- **所以**：第一次看到差异，先怀疑导出，再怀疑被检对象
- **脚本**：`xcheck_model_vs_2d.py --stage export`

### G-V 数值三档判定
- **判据**：EXACT ≤0.5% ｜ MINOR ≤5% ｜ MAJOR >5% 且**必须处置**
- **为什么**：不许用"大致相当"放过 MAJOR
- **脚本**：`xcheck_model_vs_2d.py --stage value`

## 三、体系类（对流程）

### G-FI 故障注入自证 ★元门禁
- **判据**：往表里注入已知缺陷，门禁必须抓到；捕获率不达 100% 不上线
- **为什么**：这是唯一能证明门禁不是假防线的手段。
  实测：40 多条断言里大量是 `"xxx" in h` 字符串存在性检查，
  能防"代码被删"、**防不了"代码在但算错"**——注入坏实现后仍全 PASS，拦截率 0
- **脚本**：`gate_fault_injection.py`

### G-DUP 汇总表脱钩检测
- **判据**：汇总表的关键值必须等于源表实算，不许是写死的常数
- **为什么**：汇总表写死后，源表改了它不跟随
- **抓过**：某桥梁成本是硬写死的 65572248，B4 改了它不跟
- **脚本**：`gate_drawing_basis.py`（把汇总值作为基准项纳管）

### G-PROP 方案级口径分离（1.1.0 起有脚本）
- **判据**：基础方案直接费 = Σ(非 OPTIONS 行金额)；OPTIONS 须单列不计入。
  **且必须与汇总表核对**——单看本表只能发现"少了一个 OPTIONS"，发现不了"漏标"
- **为什么**：口径错比算量错更隐蔽——算量错体现在某一行，
  **口径错让整份报价的方案归属错误**（业主一眼看出报价里有个不该有的东西）
- **抓过**：可选项 2390 万混进了基础直接费；以及"OPTIONS 行被误标成基础分部"
  （注入验证：改 1 行 CPB 编码，门禁经汇总核对报出差 186 万）
- **脚本**：`gate_scope_options.py`（**必须带 `--summary`，否则漏标抓不到**）
- ⚠️ OPTIONS 行若 CPB 编码为空，无法判归属，默认计入基础——门禁会WARN 提示这类行
- **段头继承（1.2.1 补漏）**：分段式表格只在段头行写 CPB 编码，明细行第 1 列是空的。
  直接取本行第 1 列会把整段明细判成"未标编码"——本项目 E3 实测**一次误报 34 行 / 2649 万**，
  占该表金额近六成。改为"本行有编码就用本行，没有就继承上一个段头"，并打印继承行数。
  这不是放宽：人读这张表时明细行**就是**属于上一个段头的；继承后 G-P2 反而更能抓住
  "段头是 OPTIONS、明细行没标"这种真正危险的情形，而原读法直接漏掉。
  ★段头扫描必须从第 1 行起——表头段在 `--first-row` 之上，从 first_row 起扫会让
  紧接其后的明细行凭空变成"无段头"（实测残留 8 行 / 932 万假报）
- **ack 台账（1.2.1）**：G-P1「本表确无 OPTIONS 段」与 G-P2「无段头行已确认」
  可写 `--ack`，`row=*`、`expect=n_opt=0` / `n_unlabeled=<行数>`

### G-XS 跨表/跨页签一致性（1.1.0 新增）
- **判据**：同一工作簿内两个页签指向同一实体时必须相等；
  派生值应做成跨表公式，不许两处各写一遍数
- **与 G-DUP 的区别**：G-DUP 抓"汇总值写死成常数"；本门禁抓
  **两处都是活的、看起来都自洽、但同步链断了一环**
- **抓过**：源表改了，`1_全项目成本汇总!C7` 已同步，
  同一工作簿的 `2_完整成本结构!D10` 还停在前一天的旧值——
  **两侧各自都对，中间断了 5585 万，而当时全部门禁全绿**
- **脚本**：`gate_cross_sheet.py --map <映射.json>`
- ⚠️ 映射文件写"页签!格"；该门禁**不接受 `--sheet`**（页签在映射里指定）
- **★4.5.1 修假红**：旧版只 `load_workbook(data_only=False)`，遇到 openpyxl
  生成的表（公式有 `<f>` 无 `<v>` 缓存值）拿到的是公式字符串，一律判
  「存在非数值」→ 整张表假红。实际表是对的，Excel 一打开就有数。
  现改为**双读**：公式仍由 `data_only=False` 识别，数值回落到 `data_only=True`；
  缓存也取不到时如实记**未运行（exit 2）**，不再冒充「脱钩」。
  实测同一张表：修前 `[FAIL] 存在非数值`，修后 `[PASS] 4/4 分部 + 合计一致`。
  **假红比假绿更耗人**——出现过一次，整条门禁就会被跳过。

### G-CHAIN 尺寸链闸门（4.5.1 新增）★补「关系读错」盲区
- **判据**：图纸尺寸链写成三类断言——**闭合**（Σ分段 = 总尺寸）、
  **可行性**（子项 ≤ 包容尺寸）、**同质性**（max/min ≤ 1.10）。
  任一阻断项非空即 FAIL；`level="warn"` 的判据只登记不阻断。
- **为什么要有它**：前四层门禁（公式 / 基准 / 口径 / 跨表）比的都是
  **"表里的数" vs "我读出来的数"**。两边是同一版错读时，一起错就一起对——
  **尺寸链不闭合时，"数值与图纸一致"也是假通过。**
- **抓过**（2026-10-29 阿尔及利亚 ANESRIF 铁路桥 VIADUC PK295+300）：
  第一版 17,306 m³ 与第三方 15,631 m³ 只差 11%，G-FRESH/G-DWB/G-UNIT 全绿，
  回图复测发现 **6 处读图错误**（两个数接近是错误互相抵消）：
  - 桩 4 排 × 3.60 = 10.80 m 装不进 9.60 m 承台（**可行性**）
  - `0.69+9×1.28+0.69` 的 9 是**间隔数**，片数是 10（**闭合**）
  - 5 个剖面直接平均得 0.948，其中 2 个是横隔梁实体断面，离散度 1.72（**同质性**）
  - 4.35 是柱**中心距**被当墙宽、1.60 是**边距**被当墙厚
  - 墩高双重扣减（承台顶当基准又扣盖梁 1.50，应 2.00）
  - 桥面板只算梁间带 3.54 m（板为全宽构件）
- **关键设计**：①**导入即校验**——`verify(strict=True)` 放模块级，
  任何下游脚本 import 就先过闸，改错常量整条流水线出不了表；
  ②**分级**——阻断项必须为 0，待核项登记不阻断，避免把数据瑕疵伪装成通过；
  ③**常量唯一来源**——链里禁止写字面量（本桥回归测试当场抓到：链里硬写了
  盖梁高 2.00，改常量时链不联动，判据在守另一个数）。
- **脚本**：`chain_check.py run --spec <尺寸链>.json` / `chain_check.py selftest`（7/7）
- **文档**：`references/dimension-chain-gate.md`


### G-XD 跨图一致性（4.6.0 新增，4.6.1 重订口径）★补「两图两个值」盲区

- **判据 XD1~XD5**（编号与文档 R1~R6 的映射见下表，两套编号并存时以本节为准）：
  - **XD1 版本闸**：**同一图号**且 `hash` 不同 → `RULE_CONFLICT`，不出"一致/冲突"结论。
    **不同图册 `rev` 不同不算分裂**——继续比，标「跨版对照」，须按修订表/修订云线确认
    该参数未被触及。（旧口径"rev 不同即停"会让项目中期 22 项全阻塞，是假红发生器）
  - **XD2 溯源完整**（= R1）：每侧必须有「图号 + 图面位置」，缺一 → `UNVERIFIABLE`；
  - **XD3 容差分类**（= R3）：标高/结构 ±0、**派生标高 ±10 mm**、装修 ±5 mm、
    角度 0.1%、计数 ±0。同一张表里不许用统一容差；两个方向都会错——
    ±5 mm 会放过"3600 vs 3300"，±0 比派生值又会把合规高程链全判死；
  - **XD4 缺项不折算**（= R4）：一侧缺值 → `UNVERIFIABLE`，**不得判 PASS**；
    全篇未填 / 全篇 N/A / 一项都没通过 → **exit 2**（没查不是通过）；
  - **XD5 同范围**（= R6）：两侧 `scope` 不同（全楼 vs 单层、单幅 vs 双幅）→
    `UNVERIFIABLE（范围不同）`，**不判 CONFLICT**。不补这条，计数项常年假红。
- **为什么要有它**：此前三道门禁各管一段——`chain_check` 管**一张图内**尺寸链，
  `gate_cross_sheet` 管**一个工作簿跨页签**，`xcheck_model_vs_2d` 管**模型 vs 二维**。
  **"平面图说层高 3600、剖面图说 3300，按哪个算"没人管。**
- **矩阵**：**4 组 22 项**（平面×立面 5 / 平面×剖面 6 / 立面×剖面 5 / **建筑×结构 6**）。
  D 组（轴网与总尺寸 / 构件厚度 / 梁底 vs 净高 / 踏步数×踏步高=层高 / 基础埋深 / 层数）
  是 4.6.1 补的：房建真实事故多在建筑与结构之间，一错就是一整层。
  结构项目替换为「平面 × 纵断面 × 横断面」，参数换名、方法不变。
- **关键设计**：①**六种结论**（PASS / CONFLICT / UNVERIFIABLE / RULE_CONFLICT / UNFILLED / N/A）——
  "没法比"与"比了不一致"必须分开，"没查"与"查了没通过"更要分开；
  ②**版本闸只拦真分裂**（同图号两内容），见 XD1；
  ③**反向断言**——等价换算（3600 mm vs 3.6 m）与容差内的项绝不许出现在 CONFLICT 里；
  ④**法语数值写法**——`3,60` 按 3.60 解析、`1 250` 按 1250 解析、逗号后 3 位判歧义不猜。
- **强制范围**（**该跑的时候跑，不该跑的说清不适用**）：
  房建/多图册 与 道桥（有纵断+横断+平面）**强制**；
  单图册无第二视图 → 判 **N/A 并写明理由**，不报红。**不得为了"跑过"而虚构校验对。**
- **顺序不能反**：`chain_check`（图内）→ **G-XD（图间）** → `gate_basis_freshness`（基线可信）
  → `gate_drawing_basis`（量 vs 基线）。图间不一致时"量 vs 基线一致"也是假通过。
- **脚本**：`cross_drawing_check.py init/run/selftest`（selftest **34/34**，含 3 条反向断言、
  2 条未填识别、**5 条退出码断言**——判据对而退出码错，等于门禁没接上）
- **文档**：`references/cross-drawing-consistency.md`

### G-XSC 映射覆盖率（1.2.0 新增）
- **判据**：映射文件声明 `coverage{sheet, code_col, min_coverage, exclude[]}` 后，
  从 `pairs`/`sums` 引用的单元格反查所在行 → 得到"被映射覆盖的编码集合"，
  与源表全部编码比对；未覆盖且不在 `exclude` 里 → FAIL
- **为什么**：**"映射不全"是跨表门禁唯一的失效方式**——没登记的项，它连看都不会看。
  不声明 coverage 时门禁只能提示"无法证明覆盖全表"，不能宣称"无脱钩"
- **抓过**：箱涵混凝土批次表 10,127.7 m³、主表 4,911.13 m³，跨表门禁**当时是绿的**，
  因为箱涵那几行压根没进映射（实测覆盖率 11%）
- **顺带抓**：`exclude` 里的编码在源表已不存在 → 映射过期（表改过编码/删过行）
- **脚本**：`gate_cross_sheet.py`（coverage 块可选，缺省不启用＝向后兼容，但会 INFO 提示）

### G-UNIT 单位量纲一致性（1.1.0 新增，刻意只出 WARN）
- **判据**：同一单位符号下的单价分桶后，是否有行**整档偏离主桶**
- **为什么不用别的判据**：四版判据被注入验证逐一推翻——
  ①「跨数量级」误报（湿接缝 31 m³ 与承台 14582 m³是正常尺寸差异）
  ②「偏离中位 >10 倍」漏报（注入把中位数也抬上去）
  ③「绝对区间」漏报（区间太宽，15000 落在里面）
  ④**「整档偏离主桶」才抗注入**（不依赖中位数，也不依赖固定区间）
- **为什么只 WARN 不 FAIL**：离群可能是①特殊材料（高强/预应力）
  或 ②量纲错配。**机器不该替人判**，它的作用是让你看见这一档
- **抓过**：同表内桥1 记m³、桥2 记 m³×10，交叉复核长期报 −90% 假差异
- **v4.2 单位治理**：单位符号先剥离用途括注再归类（`M3（净量）`→`M3`），但**格式归一不等于批准歧义单位**。清理后的 `CM` 仍不在全局体积白名单中；只有单位别名注册表明确绑定当前项目、量纲、合同来源条款、批准人和批准日期后，才允许按项目约定解释为体积。不带映射时 `CM` 必须被识别为未知/歧义单位并触发门禁，不得猜作体积。回归测试验证无映射失败、正确批准映射通过、项目编号不匹配再次失败；这取代了把 `CM（综合）` 全局认定为体积的旧逻辑。
- **ack 台账（1.2.1）**：`--ack` 只放行**已人工确认且理由可核查**的行；
  指纹不符报 `G-U2-ACKSTALE` 并**照常计 WARN**（ack 不能自动续期）。
  台账里 `row=*` 表示整表级判据
- **脚本**：`gate_unit_consistency.py`
- ⚠️ **量的绝对大小不能用来判量纲**——小构件与大构件天然差几个数量级

### G-DW 量纲—单位—口径词三处自洽（2.0.0 新增）★补"跨列矛盾"盲区

- **判据**（跨列比对，任一命中即报）：
  - **DW-1 FAIL** 单位列量纲 ≠ 口径声明文本里**复述该量**时所用的量纲
    （判定方式：只指证"文本中数值 == 工程量列数值"的那个数字的后缀单位）
  - **DW-2 FAIL** 有数值却无单位列
  - **DW-3 FAIL** 口径标识列不含任何**范围口径词**（全桥/单幅/两侧/每座…）
  - **DW-4 FAIL** 口径声明/依据类型列不含**证据强度词**（图纸确认/推算/估算/待核）
  - **DW-5 FAIL** 证据强度为"估算/推定"却无**可核查去处**（RFI/台账/业主清单编号/规范条款号/图号）
  - **DW-6 WARN** 口径禁用词（已计量/已确认/复核无误…）
  - **DW-7 WARN** 单位符号带括注未归一（`CM（综合）`/`M3（净量）`）；括注剥离后仍须由核心单位注册表/项目审批别名确定量纲，`CM` 不可全局猜作体积
- **为什么要有它**——真实事故（本项目，躺了两轮没人发现）：

```
CBS-OVA-A02 防冲刷保护
   单位列   = SM            （面积）
   口径声明 = 回图裁决 3252 m³（体积）
两边各自都有出处，却互相矛盾。
```

它逃过了当时所有门禁，原因值得记下来：

| 门禁 | 为什么没抓到 |
|---|---|
| `gate_unit_consistency` | 只查"单位符号在不在白名单" → SM 合法，PASS |
| `gate_scope_declaration` | 只查"口径词在不在" → 写了"全桥"，PASS |
| `gate_drawing_basis` | 比的是"量对不对基准" → 基准自己也写 3252，PASS |

  **根因：没有一道门禁跨列比对。** 每道门禁都只看自己那一列，
  而矛盾恰恰存在于**列与列之间**。

- **判据被实测推翻的记录**（写完觉得"够严"不算数）：
  - [R-DW-1] 初版扫描整行文本，只要出现"别的量纲的词"就报 FAIL。
    实测在 VIADUC 表上**误报 5 处**：钢筋行单位 MT 而文本写 `≈150 kg/m³`
    被判"出现体积量纲"；体积行文本里有 `1.05m` 被判"出现长度量纲"。
    根因是没区分**工程量单位**与**含量/描述单位**。
    修正：先剥含量单位，且只指证"数值等于工程量列"的那个数字。
  - [R-DW-2] 初版把"证据强度"和"范围口径"在同一列检查 → 全表误报。
    修正：拆成 `--scope-col` / `--evidence-col` 两个参数，分别出 DW-3 / DW-4。
- **抓过**：A02 单位 SM 而口径声明写 3252 m³（注入回测确认可捕获）
- **脚本**：`gate_dimension_wording.py`（含 `selftest` 元门禁，捕获率必须 100%）

```bash
python scripts/gate_dimension_wording.py <表>.xlsx --sheet <页签> \
  --code-col 2 --name-col 3 --unit-col 4 --value-col 5 \
  --basis-col 8 --scope-col 9 --evidence-col 12 --json out/dw.json
python scripts/gate_dimension_wording.py selftest --out out/
```

### G-XST 期望总额闭环（2.1.2 新增，借鉴 pk-boq-compare 的 `--expect-total`）
- **判据**：对**人工声明**的期望总额逐项求和比对，容差内才认；单位不同即 FAIL，
  跨单位必须显式声明换算因子与来源（G-XST5 只执行不验证）
- **为什么**：业主清单给的总数（如 3718 m³）是**唯一的外部锚**。
  2026-10-24 对比 openclaude 单遍算量，我方 4/4 闭环、它一项都对不上——
  那次闭环是**人拿计算器对的**。人对一遍，下一轮改表后就断了：
  没有闸门的闭环等于没有闭环。
- **抓过**：本技能自身——v2.1.0 及以前，"13/13 门禁全绿"里 G-UNIT 检了 0 行、
  G-PROP 算了 0.00 元。**没有期望值时，全绿不说明任何事**（见 `failure-modes.md` F-N4）
- **配套硬约束**（都在脚本里，不在文档里）：
  - XST1 期望项一行都没匹配到 → FAIL（漏项与 match 写错都看得见，输出指到具体项）
  - XST3 单位不一致且未声明换算 → FAIL（禁静默换算，不把量纲错洗成小数点错）
  - XST4 匹配集内父子名称互相包含 → WARN，可 ack（防"父级条目重复计"）
  - 公式单元格按未计量处理，改表后需重跑
  - 0 数据行 / 空期望值 / 文件页签 JSON 有问题 → exit 2（未运行，不是通过）
- **期望值文件由人填**，AI 不代填：

```json
{
  "source": "业主 BOQ 2026-05 第 6.05/6.25/6.27/6.36 项（人核后填入）",
  "tolerance": 0.01,
  "expectations": [
    {"id": "6.36", "match": "箱梁", "unit": "CM", "expect": 3718.0,
     "note": "梁板 3403.50 + 横隔梁 315 = 3718.5"},
    {"id": "6.05", "match": "梁板", "unit": "EA", "expect": 130}
  ]
}
```

`match` 可以是字符串，也可以是字符串**数组**——业主把几项合并成一个总数时
（如 6.36 = 梁板 + 横隔梁）写 `"match": ["预应力梁板", "横隔梁"]`，
数组内任一名称命中即计入。单位始终按**期望值单位**过滤，
所以 `"支座垫石"`（CM）不会把 `"支座垫石钢筋"`（MT）一起算进来。

- **脚本**：`gate_expected_total.py`（含 `selftest`：7 场景退出码全对才算上线）

```bash
python scripts/gate_expected_total.py <表>.xlsx --expect takeoff/expectations.json
python scripts/gate_expected_total.py selftest
```

### G-EXIT 门禁自身的执行失败必须可区分（1.1.0 新增）
- **判据**：退出码 `0` 通过 / `1` 检查不通过 / **`2` 门禁自身执行失败**
- **为什么**：映射文件不存在、JSON 写坏、表打不开——这些会让 Python 崩栈，
  而**崩溃时退出码也是非零**，不区分就会被调用方读成"抓到了"。
  实测踩到：第一次注入自证显示"抓到脱钩"，实为门禁自己没跑起来
- **抓过**：同上（假通过）
- **要求**：调用方（尤其注入器）**必须把 exit 2 判为"不算抓到"**

### ACK 台账（1.2.1 新增，`ack_util.py`）

**解决的问题**：WARN 型门禁（G-U2 / G-OWN3 / G-P1 / G-P2）人判完之后，
下一轮重跑**同样的 WARN 又出现**。只有三条路：
①放宽判据 → 真错一起放过；②每轮人工重看 → 做不到，看着看着就不看了；
③**把"已确认"写成可复算的台账条目** ← 本模块。

> 针对的失败模式是「人一旦见过假红，就会开始无视红灯」。
> 消除假红不能靠让门禁闭嘴，只能靠**把人的判断变成有指纹、会被反查的条目**。

**CSV 列**：`gate, table, sheet, row, expect, reason, date, by`

| 列 | 要点 |
|---|---|
| `table` | 工作簿文件名，**精确匹配**。必须存在——B3/B4/E3 页签名都叫「1_成本取量总表」、行号都从 3 起，只用 (gate,sheet,row) 做键会**一张表的 ack 替另一张表背书** |
| `row` | 行号；成对判据写 `59+60`（升序）；整表级判据写 `*` |
| `expect` | ack 当时的数值指纹，如 `qty=87360.00|price=200.00` |
| `reason` | **必须指向可核查依据**（图纸 / 招标文件 / 指标报告），少于 8 字直接不收 |

**三条防呆机制**（都已注入验证）：
1. **指纹不符 → `ACK-STALE` 且照常计 WARN**：行被改过，ack 不能自动续期
2. **未触发的条目 → `ACK-STALE` 反查**：行删了/判据不再适用，僵尸 ack 会让"已确认"失去含义
3. **按 gate 过滤反查**：一份台账被多支门禁共用，不过滤会把别的门禁的条目报成僵尸

**不接受 ack 的判据**：G-OWN4（整倍数）——命中的形态就是本项目真实踩过的错法，
一旦允许"这次是巧合"的豁免，这条门禁就在最关键的那一类错上失效。

## 五、新增门禁时的要求

1. **必须写清它抓过什么**。抓不到东西的门禁不要加。
2. **必须是数值型判据**。字符串存在性检查（`"xxx" in code`）只能防删除，不能防算错。
3. **加完必须注入验证**——造一个它该抓的错误，确认它真的报红。
4. **不重复覆盖**。同一类错误（如口径错）用一个门禁覆盖即可，别堆数量。
5. **判据必须扛得住注入**。本库里有**四版被注入验证推翻的单位判据**，
   留痕在 `gate_unit_consistency.py` 的注释表里——
   **写完觉得"够严"不算数，要让注入告诉你它到底抓不抓得住**。
6. **区分「注入无效」与「门禁无效」**。前者是调用链缺陷（目标页签选错、
   参数没传），后者才是判据太弱。**两者计入捕获率的方向完全相反**——
   分母必须只算成功注入的用例，否则会把调用链问题当门禁问题去修。
