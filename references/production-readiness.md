发布套件为 `QTO-RELEASE-SMOKE-V12`（34 项）；`--extended` 见当次运行日志。
两条新自证并入 `critical_regressions`，非 `--extended` 也执行。

**边界（必须同时读）**：
- G-XD 在**同基准、同范围**的两侧之间判定一致性。**同一图号两个内容**判 `RULE_CONFLICT`、
  不出结论；跨图册 rev 不同**不判阻塞**，标「跨版对照」，须人工按修订表/修订云线确认该参数未被触及。
  缺失、缺溯源、范围不同、数值写法歧义判 `UNVERIFIABLE`——**它不是通过，是没查到**，须原样列出。
- `render_tiles.py` 的字高只能从文字层量；转曲图与扫描件量不到，此时全部 tile 未校验 →
  **exit 2**（"没测到"不是"通过"），须改用 tile 精读指令人工复核。
- G-XD 不判断"哪个值对"。发现冲突的处置是挂 OI + 该参数下游量不出交付值（H33），
  **裁决权在设计/业主，不在算量方**。
- 切块字高判据按 **p10**，不是 min。min 单列备查（`--stat min` 可切最严）。
  字高只反映"能不能读清"，**不反映读得对不对**——读法本身仍只能靠人工回图复核
  （`human-review-loop.md`）。
- `render_read_text` 定为 medium 的**前提是可复现**：tile 坐标 + 字高都记了才算。
  记不下来的一律降 `render_read_est` 并挂 RFI。

`Chain.classify()` 按腹板宽/底翼缘宽比值分档，并校验组内同质、组间面积单调。
需要人判断的只剩"选哪个量当判别量"这一层。已通过的软件测试仍不等于真实项目验收。

## 1. 目的与边界

本文件把工程算量的可追溯性、合同计量规则、门禁状态、软件验证和正式交付分开管理。技能内置自检只能证明相应测试用例在当前环境下的行为，不代表真实项目的缺陷捕获率，也不替代设计确认、QS 复核、合同解释或授权签发。

## 2. 工程量数量基准必须显式区分

每条数量应标注 `quantity_basis`，允许值建议为：

- `DESIGN_THEORETICAL`：根据设计几何与参数计算的理论量。
- `CONTRACT_MEASURED`：按合同约定的计量规则计算的合同计量量。
- `TENDER_BOQ`：投标或合同 BOQ 所载数量。
- `SITE_CLAIMED`：根据现场记录申报的数量。
- `CERTIFIED_PAYMENT`：经合同授权人员确认的支付/认证数量。

不得因为某两种数量不一致就自动认定其中一方错误。必须先核实范围、图纸版本、计量规则、施工记录及合同机制。

## 3. 计量规则注册

每条规则应具有唯一 `rule_id`、适用专业、司法辖区/项目范围、来源文件和版本、合同条款、计量边界、计入项、扣除项、单位、舍入规则、批准状态和测试用例。候选标准（例如 NRM、CESMM、POMI 或项目自定义规则）只能在合同确认后采用；不得同时假设多个规则体系自动适用。

当规则缺失或冲突时，状态应为 `DRAFT` 或 `RULE_CONFLICT`，并提出明确的确认问题。不得以“国际惯例”填补没有来源的系数或合同条款。

## 4. 门禁状态契约

所有运行器和报告应区分：

- `PASS`：检查适用、实际执行，且未发现违反判据的问题。
- `FAIL`：检查执行成功，并发现一项或多项不符合。
- `NOT_RUN`：未执行、不适用、没有可检查行或前置条件不满足；必须说明具体原因。
- `ERROR`：门禁本身无法完成，包括异常、输入解析失败或依赖缺失。

空输入、零行、没有匹配列、无期望值或不适用的数据不得自动计入通过。运行报告应记录实际检查行数、预期行数、跳过数、发现数、输入摘要、规则版本和软件版本。

## 5. 证据与覆盖要求

总体读数台账覆盖率仅是筛查指标，不能单独决定是否交付。关键构件、高风险数量、合同敏感项和影响多个下游计算的参数必须逐项满足项目证据要求。每项数量至少应能追溯到：

1. 图纸/模型文件 ID 与修订版；
2. 图面位置或模型实体 ID；
3. 原始参数及单位；
4. 使用的计量规则 ID 与版本；
5. 公式、扣减/加项及舍入策略；
6. 数量基准和证据等级；
7. 复核状态及修改记录。

不能取得充分证据时，数量应标为待核或推定，且按项目政策限制其用途。不得将推定量混入已确认承诺量而不作标识。

## 6. 图纸版本与影响分析

文件哈希变化是重新审查的触发条件，不是工程量变化的证明。文件名相同也不证明文件内容相同。每次变更应记录旧版、新版、差异范围、受影响的参数、数量行、汇总节点、BOQ 项和复核/审批状态。若无法建立可靠的影响范围，应扩大复核范围并说明原因。

## 7. 二维/三维交叉复核的独立性

两侧数量完全相同不必然表示共模；两侧有差异也不证明独立。独立性评估应查看参数来源、模型构建路径、导出工具、共用中间文件、公式实现及复核人员。零差异比例和相同来源词只作为风险信号。对几何离散、容差和舍入造成的差异，应单独解释，不应人为修平。

## 8. 测试与发布

每个强制门禁至少应具备：正向缺陷测试、合法输入反向测试、边界测试、空输入/不适用测试、输入损坏测试，以及对既有项目样例的回归测试。故障注入应只修改临时副本，并检查原始输入前后摘要一致。

测试报告必须标明测试集范围、成功注入数、跳过数、反向误报断言、运行环境和版本。不得把有限测试集中的 100% 捕获率宣传为生产缺陷捕获率 100%。

发布前应执行：

1. Python 编译检查；
2. 环境与依赖检查；
3. 所有脚本自检；
4. 规则库 schema/完整性检查；
5. 门禁正反向和边界回归；
6. 至少一套经授权脱敏的端到端项目样例；
7. 交付文件与批准输入版本一致性检查；
8. 变更记录、已知限制和回滚包检查。

## 9. 交付放行原则

只有当范围已确认、适用计量规则已确认、关键数量证据满足要求、强制门禁均已执行、阻断项关闭或经授权书面接受、独立复核完成、交付版本一致且授权人员签审后，才可标记为正式交付。

AI 或自动化工具不得代替设计确认、合同解释、支付认证或项目授权人员签发。任何例外必须有责任人、理由、影响范围、有效期限和批准记录。

## 10. 已知限制

v2.2.0 增加的是治理模板和交付规则，并不意味着现有所有脚本都已自动实现上述所有字段或状态契约。项目采用时应逐项核对工具实际输出；未实现的能力应明确标为待开发，不得仅因文档存在就宣称已经自动化。
