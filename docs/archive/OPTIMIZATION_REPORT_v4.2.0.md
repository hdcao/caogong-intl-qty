## 2. 已落地的主要改进

### 2.1 项目与计量规则发布前预检

新增 `scripts/qto_project_validate.py`，将项目清单、计量规则注册表、单位别名注册表纳入统一预检，检查项目/技能包版本漂移、规则 ID 重复、适用日期、物理量纲、范围包含与排除冲突、文件缺失、相对路径逃逸、审批状态、强制门禁、未处理占位符和生产发布条件。

新增四份 JSON Schema：项目清单、计量规则注册表、项目单位别名注册表、统一门禁结果。结构校验与语义/专业审批分离；Schema 合法并不等于合同规则已批准。

### 2.2 单位量纲统一治理，移除 `CM` 的全局默认解释

核心单位注册表成为 G-UNIT 和相关检查的量纲来源。`CM` 不再被全局词表默认为体积；仅当项目单位别名注册表提供当前项目适用范围、目标单位/量纲、合同来源文件与条款、批准人、批准日期等完整治理信息时，才能按项目约定解释。

回归覆盖三种情况：无审批映射时阻断；有效且项目匹配的映射可通过；项目编号不匹配时重新阻断。通用示例改用 `M3`/`m³` 等无歧义单位。

### 2.3 门禁结果契约与发布证据

`GateResult` 明确区分 `executed` 和 `status`；未执行检查不能隐式 PASS；严重级别不能被后续低级别问题降级；无效计数会产生明确错误。遗留门禁未提供检查计数时，在标准化契约中保留 `null`，不伪造覆盖率。

端到端流程为每个步骤生成标准 GateResult JSON，并区分命令执行状态与门禁发现状态。当前 `--skip-smoke` 只接受当前套件 ID、完整 42/42 结果、当前源树的两次 SHA-256、源树未变标志和无失败标记的测试证据；旧版、分母错误、日志不完整或被篡改的证据都会被拒绝。

### 2.4 安全、确定性和错误处理

- CSV 公式注入检查覆盖 Unicode 空白、前置 Tab/换行等情形，同时保留合法负数文本。
- JSON 集合型字段按稳定顺序序列化，减少无意义的报告差异。
- 测试运行器对超时/启动失败明确记 FAIL，并终止进程组，避免后台子进程持有输出管道而使总测试卡死。
- 发布测试在开始与结束时重新计算源树指纹；源文件被意外修改时，即使检查数量全通过也不能发布为 PASS。
- 房建与道桥开项清单/说明文档编号不一致时阻断，而不再只给 WARN。

## 4. 建议的实际使用顺序

1. 从 `INSTALL.md` 安装 Python 依赖并运行环境自检。
2. 在真实项目根目录编制项目清单、合同计量规则注册表、图纸基准和单位别名注册表。
3. 执行 `qto_project_validate.py`；未批准规则、歧义单位、路径/版本错误和占位符应先解决。
4. 读取图纸、形成可追溯的算量证据，再执行结构、范围、量纲、单位、总量、公式、跨表和 BOQ 门禁。
5. 对真实项目建立独立黄金样本与负向样本，由 QS/工程师复核关键数量和差异；最终放行须由授权人员签审。

## 5. 仍然明确保留的边界

- 当前端到端项目全部是虚构测试数据，不能代替任何真实项目的黄金样本。
- 机器不能自行决定合同采用 NRM、CESMM、POMI、地方规范还是项目专用规则；必须按合同及批准文件配置。
- PDF 矢量探测是取证/诊断，不等于自动把所有图元转换成可靠工程量。
- 二维与模型对比只有在输入源独立性、范围与口径得到证明时才有实质独立复核意义；测试夹具只验证预设的数据路径。
- 部分遗留门禁没有原生的 checked/expected 行数，统一契约如实留空；未来需逐个专业门禁补齐计数和黄金样本。
- 软件测试通过不等于真实项目的合同合规、设计确认、签证有效性、市场单价合理性或付款认证。

**发布建议：** v4.2.0 可作为本轮优化的稳定基线。生产项目仍需完成项目规则审批、真实输入版本核验、黄金样本验收和专业签审，不应跳过这些外部工程治理环节。
